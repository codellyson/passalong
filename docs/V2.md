# V2: Passalong as a task queue for agents

**Version:** 0.1  **Author:** Lukman Isiaka  **Date:** 2026-09-21  **Status:** Built, not yet deployed. Next: deploy, then two weeks of dogfooding

## 1. One-liner

You queue work as task cards. Agents claim cards, do the work, and bring back a report. You approve or reject each report at a gate.

## 2. Why this and not a plain "Trello for agents"

Kanban boards are a commodity. Linear, GitHub Issues and Jira already let you assign tickets to agents. Passalong's edge is what the card carries: a structured brief goes in and a transfer guide comes back, with the decisions, the steps and how the work was verified. The queue sits on top of the handoff product we already have. It does not replace it.

- Extend, not pivot. Guides stay the unit. The task board is a second view beside the existing handoff queues (`waiting, not working, in flight, landed, promote`).
- No tracker integration in v2. Linear comes first after that, because its buyers match ours.
- Solo developer first: one person, many agent sessions, one board. Team plumbing already exists and comes next.

## 3. Who runs the agent

v2: a human opens a session and tells the agent to take the next card, and the agent calls `next_task` over MCP. Passalong runs no agents itself.

Next: a `passalong work` loop that spawns `claude -p` for each card on the local machine. Cloud runners are out of scope because they would make us a hosting company.

## 4. The task card

New `kind: task`, next to `transfer` and `bug`.

```markdown
---
kind: task
title: ...
target_context: owner/repo   # optional
blocked_by: [id, ...]        # optional
---

## Goal
## Context
## Constraints
## Acceptance
## Out of scope
```

- **Authoring.** `passalong task "<sentence>"`: the agent drafts the card, you edit it in your editor, and the card lands in Draft. This is the same pattern as capture.
- **Planner.** An agent splits a large goal into several cards. Planner cards always land in Draft. A human moves them to Ready, one at a time or all at once.
- **Routing.** `next_task` returns only cards whose `target_context` matches the session's repo. A card without `target_context` goes only to sessions outside any git repo, or to `next_task` with `any`. For a new project, the agent sets `target_context` after it creates the repo. There are no multi-repo cards: split the work into one card per repo and link them with `blocked_by`.
- **Dependencies.** `next_task` skips blocked cards. A card unblocks only when its blocker passes the human gate, not when an agent says it is done.

## 5. Claim, lease and lifecycle

No two agents may work on the same card at the same time.

- **Atomic claim.** The server moves a card from `ready` to `claimed` with one compare-and-set that records `claimed_by`. A second caller gets a different card. The task board therefore needs login, and the server owns every claim.
- **Lease.** 30 minutes. `task_progress` and `next_task` from the claiming agent renew it. `task_progress` carries a one-line status, and the board shows the latest line.
- **Expiry.** When the lease expires, the card moves to `Stalled` and stays locked. It never goes back to Ready on its own. Only you release it (`passalong release <id>`, or **Take it back** under Taken), or the same agent resumes it. Releasing is every kind's now, not a task's: a handoff has one claim per repo and one call takes it back from all of them. A stalled card keeps a pointer to its branch or worktree, so the next agent continues that work instead of starting over.
- **Agent identity.** On first MCP connect, each worktree mints one stable id and stores it in `.passalong/agent.json`, which is git-ignored. The server records host, repo and worktree path against the id for display. The id survives restarts. A new worktree gets a new id.

Columns:

```
Draft → Ready → Claimed → Review → Done
                   ↓
                Stalled            Blocked is derived from blocked_by, not a column
```

- **Finish.** `finish_task` runs capture. It attaches a transfer guide and a PR or branch link, and moves the card to Review.
- **Gate.** You approve or reject on the web board or in the CLI. A rejected card goes back to Ready with the reason appended, so the next agent sees why.

## 6. Vocabulary

A brief goes in and a report comes out.

- `task` and `bug` are briefs: work to do.
- `transfer` is a report: work done. A handoff is a report sent to someone else.
- The frontmatter `kind:` values stay `task`, `bug` and `transfer`, so existing guides and MCP instructions keep working. The CLI keeps `guide` aliases.

## 7. Business

- Included in the current paid plan during v2.
- Primary metric: the share of cards that pass the human gate on the first attempt. A low rate means the queue creates review work instead of saving time.
- Secondary metric: paying users who create more than 10 task cards a week.

## 11. Next: one entity

**Status:** Agreed 2026-09-22. Built locally, all five slices; not deployed.

Tasks and handoffs are not two things. A guide is one unit of work handed from one context to another. `kind` picks the body's template and nothing else: no separate flow, tools, page or ownership model per kind.

- **Default kind is `task`.** Most use is assigning work. Every authoring surface (`passalong new`, the web writer, `publish_guide` with no kind) starts a task and writes `kind: task` into the frontmatter. A guide with no `kind:` line still reads as `transfer`, because every installed CLI and the v1 capture flow write transfers without one. Flipping what "absent" means would turn their handoffs into tasks. Stored rows with an empty kind are backfilled to `transfer` once.
- **Destination.** A guide goes to a person, a group, a team, a repo (`target`), or a team plus a repo. A repo is what the task queue is today.
- **One lifecycle.** `draft → open → taken → handed in → done`, with `passed` and `taken back` returning it to open. "Handed in" merges today's task review and today's verdict: here is what I did, and did it work.
- **One claim model.** Taking any guide writes a claim: who, agent, host, worktree, lease, last note. This is the existing `claim` table. The lock is one taker per guide per repo. A task or bug has one repo, so it has one taker. A transfer sent to a team can be repeated in several repos, one taker in each.
- **One closing gate.** The author closes what was handed in, or sends it back with a reason. A handoff marked "worked" closes in one click.
- **A follow-up is never handed over alone.** Follow-ups travelled one way: opening a guide handed over the guides written under it, and opening one of those handed over nothing — so an agent given a follow-up read a document that assumes work it has never seen, and either went looking for the original or treated the note as the whole job. `GET /v1/guides/:id/parent` answers the guide a follow-up came out of, with its document (clipped like a follow-up) and where it has got to: `draft`, `open`, `held` (by whom), `handed in` or `done`. `take` and `get_guide` put it in front of the follow-up on both servers, with the line that matters — if this needs that guide done and it is not, say so rather than starting. Readable on the follow-up is not readable on the parent: it is filtered again on its own, and reading it records no pull, because fetching context for a guide is not opening that guide.
- **Evidence goes against the line it answers.** One block of output answered "is this real" and left "does it meet what I asked for" to the reviewer, who read an Acceptance line — "the sixth is refused with 429" — and then hunted for `429` in a wall of text, once per line. A task's `hand_in` now takes `checks`: one entry per Acceptance line, each with that line and what ran for it (migration 0028, JSON on the claim; `evidence` is filled from them so every older surface still works). The review screen pairs them by text, never by position — a hand-in that skipped a check would otherwise file the next piece of evidence under it, and the reviewer would read a pairing the agent never claimed. A line with nothing against it says so, and evidence that answers no line is kept under "Also ran". A handoff and a bug have no Acceptance lines, so for them evidence stays one block.
- **A guide that did not hold says so, on itself.** A verdict carries `detail` and `checks` as well as its one-line `note` (migration 0030), and the share page renders standing failures above the Steps. `note` is capped at 280 characters because it is what a row shows; a correction is measurements, commands and commit ids, which is why agents published them as guides called "Correction: …" and hoped the next reader followed the link. A failing hand-in feeds its evidence straight into the verdict. Nobody is named on the share page: the key in the URL is the whole authorisation, so it is as public as the link — an author put their own name in their own frontmatter, a verifier did not put theirs anywhere.
- **A guide that worked with changes says so too.** `hand_in` on a handoff or a bug takes `writeup` (migration 0031, on the claim and the verdict): what had to be adapted to make it work where it ran — a version, a name, a step that needed something the guide does not mention. It is the last of the four things an agent had to publish a guide to say. A hand-in that HELD could answer with `ok` (a boolean), `note` (280 characters, the width of a row) and `evidence` (refused unless it is what you ran), so "the email step needs MAIL_FROM and the R2 bucket name" went out as a follow-up guide with an id, a share link and an inbox row asking somebody to take it — when it is a paragraph about the guide it was found in. Never required and never refused for its shape: it is prose about something nobody can specify in advance, and a rule about its length would only teach agents to pad it. The share page shows it under the failing verdicts and above the Steps, on its own query so a guide with five write-ups can never push a "this did not hold" off the warning; the author sees it unfolded on the handed-in row, because whether the guide itself should change is theirs to decide. A later hand-in with nothing to add keeps what an earlier one wrote: a verdict is one row per account, and silence is not a retraction. Nobody is named on the share page, for the reason the failing list names nobody.
- **Search the whole tree before you conclude.** A bug and a task both ask an agent to locate things for itself, and the recurring failure is the same on both: it lists one directory, or opens the one file it expected, and concludes from that — that the thing is absent, that it found the only occurrence, that it is already handled. The conclusion is confident and wrong, and nothing downstream can tell, because the evidence it brings is real; it is evidence of a search that was too small. `SEARCH_WIDE` is said in front of every bug and every task on both MCP servers, beside `KEEP_EVIDENCE`, in the product's own line: "I looked" is a claim; the search and what it printed is evidence. A transfer guide gets neither, as before — it is handed over untouched, and anything in front of it is one more thing that is not the document. The two mirrored blocks were held together by a comment saying they mirror each other; a test now holds them, because a comment does not fail, and a rule that reached one server was a rule half the agents never got.
- **A check is run or shown.** An image the USER showed an agent has been mandatory before `publish_guide` and `file_bugs` for as long as those existed — describing it instead of attaching it throws away the most useful thing in the report — while an image that is the only possible proof of the agent's OWN claim was never asked for once. So "a Sales Order PDF renders with the store's brand colour" came back as "opened SO-00026, the header bar is #1f6feb", passed, and nothing in the system had looked at anything. `checksProblem()` now refuses a check that is neither: put the command in `cmd` and it is executed before the hand-in lands, or call `attach_screenshot` (`create_upload` for a file on disk) and put the line it returns in `ran` — both end at `/v1/shots/<id>`, so one pattern answers for both. A command PASTED into `ran` is refused too, and that is the point rather than a side effect: the same string typed by the agent and executed by the runner is indistinguishable in the text and proves completely different things, and `cmd` is how the second one is said. A check that can be neither run nor shown is not a check; it belongs in `writeup`, where it reads as the agent's account. `passalong.handIn()` runs pending commands itself, which it never did — only the MCP server ran them, so "it is executed here" was true over one transport and a quiet lie over the other.
- **What ran outranks what was said about it.** The share page gave its best position to its weakest evidence: a passing hand-in's `writeup` — prose nothing checked — sat above the guide it was about, while that same hand-in's `checks` were not on the page at all. A 4000-character write-up pushed the first heading off the screen. The page now asks for both and sorts them: a check carrying `cmd` and an `exit` was executed by the runner before the hand-in was allowed to land and a non-zero exit refused it, so its output is the one thing on the page the agent could not have written, and it goes first with its own badge; a check with only `ran` is the agent's account of a command and is drawn as prose, not as output; the write-up comes last under "What they said they changed", bounded so it scrolls rather than becoming the page. Nothing gates the prose — no rule can tell good prose from plausible prose, and any length rule teaches padding. The answer is not to refuse it but to stop showing it where evidence belongs.
- **Every hand-in carries evidence, against the line it answers.** `checks` — one entry per line the guide asks for, `## Acceptance` on a task and `## Verification` on a handoff or a bug, each with that line and what was run for it. It was a task's shape only, so a handoff answered a list with a paragraph: the agent had nothing shaped like the question, no way to tell when it was finished, and hand-ins came back as a separately published guide titled "Hand-in evidence: …" or as `pass` with a note. `evidence` as one block is still accepted and is what a hand-in from before this, or from a person in the browser, carries: what it ran and what came back — the command and the lines that decided it, a test summary, a link to the change, a screenshot url. The write-up and the "it worked" are both the agent's word for its own work; evidence is the part the person at the gate can check, and the hub shows it under the write-up ("What it ran"). It is stored on the claim (migration 0025), refused by `evidenceProblem()` in claims.ts when it is a verdict rather than a run, and named on every `next` step so an agent reads it at take, at each progress call, and in the Stop hook rather than once at the start. A person handing in from the browser is taken at their word: that side has no terminal, and a paste box there would be the form this product does not have.
- **One tool set.** `take` (by id, or the next one: addressed to you, then your groups, your team, the queue for this repo), `progress`, `hand_in`, `pass`. `next_task`, `start_guide`, `ack_guide`, `task_progress`, `finish_task` and `verify_guide` stay as aliases for installed clients. The `TASK_TOOLS` refusal goes.
- **Agents always know the next step.** Every tool result ends with `next`: the calls that make sense from this state, with when and why, worked out by the server because only it knows the state (`take` → `progress` at milestones, `hand_in` when Acceptance holds; `hand_in` → `take` if the queue has more, else stop). Errors carry it too. On top, for Claude Code, `passalong setup` installs two hooks: SessionStart runs `passalong now` (what this worktree's agent holds, its last note, what waits), and Stop refuses to end a session that still holds a claim without `hand_in` or `pass`.
- **People hold work too, and the author closes handoffs.** Taking a handoff in the browser holds it (agent `person-<account>`, a week's lease, several at once) so Taken shows people as well as agents; saying it worked hands it in. The author closes any guide of theirs from its own row — the gate was only ever that you wrote it, and a guide whose receiver never opened it could not leave Open otherwise, because leaving needs somebody else to say it worked. Whoever it was addressed to is told. After a fortnight with nothing at all — no pull, no ack, no claim, no verdict — the hourly cron closes it and tells both sides (`staleSent`, `STALE_SENT_MS`, notification kind `shelved`). The author sees hand-ins under Needs you and closes them (the guide is archived) or sends one repo's back with a reason (`GET /v1/handed_in`, `POST /v1/guides/:id/close`, `POST /v1/guides/:id/send_back`, notification kinds `closed` and `sent_back`).
- **Reassigning.** Its author, or whoever it is assigned to (the person, or anyone in the group; the author is then told), gives a guide or task to `@handle`, `#group` or the whole team (`POST /v1/guides/:id/assign`, `passalong assign`, the `assign` MCP tool, "give to…" in the hub). The queue honours it: a task for a person or group goes only to their agents. Whoever held it and is left out has it taken back (`dropOutside()`), with a line on a task saying where it was, and is told (`reassigned`).
- **Your work, inside the assistant.** The hosted server's `work` tool gathers what needs you, who is on what and what is open; hosts that support MCP Apps (Claude, ChatGPT) draw it as a board from `ui://passalong/work`. Read-only by design: the review gate is not exposed over MCP, so its buttons open the hub.
- **Agent first, no forms.** Guides are written by the agent that has the context, over MCP or the CLI. The hub reads, reviews and decides; where it once had a form it shows the sentence to say to your agent (`apps/web/app/utils/asks.ts`). The browser writer is gone and `/hub/write` redirects to `/hub`. Deciding stays in the hub: a reason to send work back is a decision, not authoring.
- **One page.** Needs you (handed in to you to close, and addressed to you), Taken (who has what, across everything, for the team), Open, Done. It replaces the separate Tasks and Guides pages.

Migration is additive: ack rows (0013) become claims, verdicts become handed-in claims. No table is dropped in the same release.
